1. Architecture Overview

A 3-node OKD compact cluster on AWS where all nodes act as both control-plane and workers. The cluster is ephemeral — created fresh for each lab session and fully destroyed afterward. All configuration lives in GitHub; no data persists in AWS between sessions.

There is no bastion host. The cluster is managed from an external Raspberry Pi 5 running the AWS CLI, Terraform, and oc. Node shell access uses oc debug node through the API — no SSH or jump host required.

2. Lab Lifecycle

The cluster is created from scratch each session and torn down when done. The only thing that persists between sessions is the Terraform state in S3 (~$2/mo) and your Git repository.

lab-upPhase 1 — Terraform: VPC, SGs, IAM, S3, NLBs, Route53~5 min
lab-upPhase 2 — Generate ignition configs → upload to S3~1 min
lab-upPhase 3 — Launch bootstrap + 3× master EC2 nodes~2 min
lab-upPhase 4 — Bootstrap process → bootstrap node destroyed~35 min
lab-upPhase 5 — Cluster operators stabilise → cluster ready~10 min
# Start a session
./scripts/lab-up.sh

# Optional flags if resuming a failed run:
./scripts/lab-up.sh --skip-infra        # Infra already exists
./scripts/lab-up.sh --skip-infra --skip-ignition   # Nodes not yet launched

# Access the cluster
export KUBECONFIG=./cluster-config/auth/kubeconfig
oc get nodes
oc get clusteroperators

# Tear down when done — AWS cost drops to ~$2/mo immediately
./scripts/lab-down.sh
💡
All state in Git. Before running lab-down.sh, push any in-cluster config changes to GitHub via ArgoCD. The cluster rebuilds from the repo — nothing needs to survive in AWS.

install-config-template.yaml — What It Does

The OKD installer requires an install-config.yaml file that defines the cluster — region, subnets, instance types, domain name, SSH key, and pull secret. This file is consumed (deleted) by the installer when it generates ignition configs, so it cannot be reused as-is.

scripts/install-config-template.yaml solves this by using ${VARIABLE} placeholders that lab-up.sh populates at runtime using values pulled live from Terraform outputs (subnet IDs, cluster name, AZs, etc.). A fresh install-config.yaml is rendered to cluster-config/ each session — never committed to Git. 

# Simplified flow inside lab-up.sh:

# 1. Pull subnet IDs from terraform outputs
PRIVATE_SUBNET_1=$(terraform output -json private_subnet_ids | python3 -c "...")

# 2. Export variables
export BASE_DOMAIN CLUSTER_NAME MASTER_INSTANCE_TYPE PRIVATE_SUBNET_1 ...

# 3. Render template → install-config.yaml
envsubst < scripts/install-config-template.yaml > cluster-config/install-config.yaml

# 4. openshift-install consumes install-config.yaml and generates ignition configs
openshift-install create ignition-configs --dir=cluster-config/
# install-config.yaml is now deleted by the installer

# 5. Upload ignition to S3 so EC2 nodes can fetch them on first boot
aws s3 cp cluster-config/bootstrap.ign s3://<bucket>/bootstrap.ign
aws s3 cp cluster-config/master.ign    s3://<bucket>/master.ign
ℹ️
The fake pull secret {"auths":{"fake":{"auth":"aWQ6cGFzcwo="}}} is used in the template. OKD is open-source and does not require a Red Hat account or a real pull secret.

6. Node Access — No SSH, No Bastion

Nodes run Fedora CoreOS, an immutable OS not intended for direct SSH management. Three access methods are available, in order of preference:

MethodCommandWhen to UseRequires
oc debug node Primary oc debug node/<node-name> Any runtime troubleshooting Cluster running, valid KUBECONFIG
AWS SSM Session Manager Backup aws ssm start-session --target <instance-id> Node unreachable via API AWS CLI + SSM IAM policy (already attached)
EC2 Serial Console Emergency AWS Console → EC2 → Serial Console Node won't boot / kernel panic AWS Console access 
# Primary: get a root shell on any node (no SSH key, no bastion needed)
oc debug node/okd-lab-master-0   -- chroot /host

# Check node logs
oc debug node/okd-lab-master-0   -- journalctl -u kubelet --no-pager -n 50

# Backup: SSM (IAM policy already applied to master role)
aws ssm start-session --target i-0abc123def456789

12. Install Flow

  • 1
    Terraform — Core Infrastructure
    Provisions VPC, subnets, IGW, NAT GW, SGs, IAM roles, NLBs, Route53 zones + records, S3 buckets. Excludes EC2 nodes (applied separately after ignition is ready).
  • 2
    Render install-config.yaml
    lab-up.sh pulls subnet IDs from Terraform outputs, injects them into install-config-template.yaml via envsubst, writes cluster-config/install-config.yaml.
  • 3
    Generate Ignition Configs
    openshift-install create ignition-configs consumes install-config.yaml and produces bootstrap.ign, master.ign, worker.ign. install-config.yaml is deleted by the installer.
  • 4
    Upload to S3
    Ignition files are uploaded to the bootstrap S3 bucket. EC2 nodes fetch them on first boot via their user-data ignition pointer.
  • 5
    Launch Bootstrap + Masters
    Terraform applies the EC2 module. Bootstrap node (public subnet) and 3 master nodes (private subnets) start. All boot into Fedora CoreOS and fetch their ignition configs.
  • 6
    Bootstrap Process (~35 min)
    Bootstrap node brings up a temporary control plane. Masters join, form etcd quorum, and take over as the permanent control plane. lab-up.sh detects completion and immediately destroys the bootstrap node.
  • 7
    Cluster Operators Stabilise (~10 min)
    All cluster operators (console, ingress, image-registry, monitoring, etc.) come online. openshift-install wait-for install-complete confirms readiness.
  • 8
    Post-Install: GitOps Setup
    Install the OpenShift GitOps Operator, connect the GitHub repo, apply the app-of-apps ArgoCD Application. All future changes go through Git.

3× m6a.xlarge + NLBs + NAT GW + EBS. On-demand — no commitment.

The key saving: By destroying all resources at rest (not just stopping EC2), you avoid the $50+/mo in NLB + NAT Gateway idle charges that would apply if you only stopped the instances.

Design Decisions That Minimise Cost

DecisionSavingTrade-off
Full destroy at rest (not stop/start)~$50/mo~50 min rebuild time each session
m6a.xlarge not m6a.2xlarge~$0.35/hr16 GB RAM — tight for heavy workloads
Single root volume, no dedicated etcd EBS~$8/mo runningSlightly lower etcd I/O isolation
Single NAT Gateway (not 3×)~$65/mo runningSingle AZ for outbound — fine for lab
No bastion host (Raspberry Pi instead)~$17/moMust install tools on Pi

14. GitOps & ArgoCD

Install OpenShift GitOps Operator (once per session)

oc apply -f - <<EOF
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: openshift-gitops-operator
  namespace: openshift-operators
spec:
  channel: latest
  name: openshift-gitops-operator
  source: community-operators
  sourceNamespace: openshift-marketplace
EOF

# Wait for ArgoCD to be ready
oc wait --for=condition=Available deployment/openshift-gitops-server \
  -n openshift-gitops --timeout=5m

# Get admin password
oc extract secret/openshift-gitops-cluster -n openshift-gitops --to=-
